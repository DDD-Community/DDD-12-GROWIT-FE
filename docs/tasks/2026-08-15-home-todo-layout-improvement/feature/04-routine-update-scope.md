# Task 04. 반복 투두 수정 범위 확장

> 프론트엔드 변경 계획: [반복 투두 수정 범위 프론트엔드 문서](../frontend/04-routine-update-scope.md)

## 목적

반복 투두를 수정할 때 기존의 `해당 투두만 수정`, `전체 반복 투두 수정`뿐 아니라 선택한 회차를 포함한 이후 회차에만 변경을 적용할 수 있도록 한다.
사용자가 수정 범위와 데이터 손실 가능성을 저장 전에 이해할 수 있어야 하며, 배포된 서버 API 계약에 맞춰 요청과 캐시 갱신 방식을 마이그레이션한다.

## 사용자 관점 동작

예를 들어 매주 월요일 반복이 `3/2, 3/9, 3/16, 3/23`에 있고 사용자가 `3/9` 회차를 수정하면 다음과 같이 동작한다.

| 버튼 | API 범위 | 사용자에게 보이는 결과 |
| --- | --- | --- |
| `해당 투두만 수정` | `SINGLE` | `3/9` 한 건만 수정하고 나머지 회차는 유지한다. |
| `해당 날짜 이후 수정` | `FROM_DATE` | 원래 `3/9` 회차를 포함해 `3/9, 3/16, 3/23`을 수정하고 `3/2`는 유지한다. |
| `전체 반복 투두 수정` | `ALL` | 과거를 포함한 `3/2, 3/9, 3/16, 3/23` 전체를 수정한다. |

- `FROM_DATE`의 기준일은 폼에서 새로 선택한 날짜가 아니라 경로의 `{id}`가 가리키는 회차의 **수정 전 날짜**다.
- 사용자가 `3/9` 회차의 날짜를 `3/11`로 옮기고 `FROM_DATE`를 선택해도 서버는 원래 `3/9`부터 자른 뒤 본문의 `date`를 기준으로 이후 회차를 다시 만든다.
- `FROM_DATE`와 `ALL` 수정은 대상 회차를 삭제하고 재생성하므로 해당 범위의 투두 ID가 바뀐다.

## 현재 구조와 API 마이그레이션

- `EditBottomSheet`에는 `해당 투두만 적용`, `전체 반복 투두 적용` 두 선택지만 있다.
- `PutTodoRequest`에는 세 범위 타입이 이미 선언돼 있지만 `FROM_DATE`를 호출하는 핸들러와 UI가 없다.
- 일반 수정 요청은 `routine`을 보내면서 `routineUpdateType`을 생략할 수 있어 배포 API에서 400이 발생한다.
- `SINGLE` 및 `ALL` 전용 요청에서 `time`을 보내지 않아 기존 시간이 초기화될 수 있다.
- 수정 폼은 날짜 목록의 `routine`을 사용하며 `GET /todos/{id}`로 최신 회차 상세를 다시 확인하지 않는다.
- 현재 `routine` 타입은 `repeatDays`를 보존하지 못한다. 서버가 내려준 다중 요일 설정을 누락한 채 범위 수정하면 반복 일정이 달라질 수 있다.
- 현재 수정 API 타입은 응답 바디가 있다고 가정하지만 배포 API의 `PUT /todos/{id}` 성공 응답은 `200`의 빈 바디다.
- 현재 성공 처리는 폼의 날짜 한 건과 개수 쿼리만 무효화한다. `FROM_DATE`와 `ALL`은 여러 날짜와 ID가 바뀌므로 전체 투두 목록 캐시 갱신이 필요하다.

배포 문서 기준 신규 경로는 없다. 기존 `PUT /todos/{id}`의 조건부 필수값과 성공 응답 스펙이 변경됐으며, 최신 반복 정보를 얻기 위해 기존 `GET /todos/{id}` 상세 조회를 수정 흐름에 연결해야 한다. `DELETE /todos/{id}` 계약은 이번 수정 버튼 작업에서 변경되지 않는다.

## 구현 범위

### 1. 수정 범위 선택 모달

반복 투두의 수정 버튼을 누르면 다음 순서로 세 버튼을 표시한다.

```text
해당 투두만 수정          → SINGLE
해당 날짜 이후 수정       → FROM_DATE
전체 반복 투두 수정       → ALL
```

- 신규 버튼 문구는 `해당 날짜 이후 수정`으로 통일한다.
- 기존 버튼의 `적용` 표현도 사용자가 수행할 동작이 분명하도록 `수정`으로 통일한다.
- 버튼을 누른 즉시 범위 선택 모달만 닫지 않는다. 요청 중에는 로딩 상태를 표시하고 세 버튼 및 닫기 동작의 중복 실행을 막는다.
- 성공하면 목록 재조회가 시작된 뒤 편집 화면을 닫는다.
- 실패하면 입력값과 범위 선택 화면을 유지하고 재시도 가능한 오류를 표시한다.
- 닫기 버튼과 각 범위 버튼에는 접근 가능한 이름과 키보드 포커스가 제공돼야 한다.

### 2. 비반복·반복 분기 정책

모달 노출 여부는 사용자가 폼에서 바꾼 현재 `repeatType`만 보지 않고, 수정 시작 시 조회한 원본 투두의 반복 여부를 기준으로 결정한다.

| 원본 상태 | 저장할 상태 | 정책 |
| --- | --- | --- |
| 비반복 | 비반복 | 범위 모달 없이 일반 수정한다. `routine`과 `routineUpdateType`을 모두 보내지 않는다. |
| 비반복 | 반복 | 범위 모달 없이 새 반복을 생성한다. `routineUpdateType: "ALL"`과 `routine`을 함께 보내고 `routine.duration.startDate`를 본문 `date`와 같게 맞춘다. |
| 반복 | 반복 | 세 범위 선택 모달을 표시한다. |
| 반복 | 비반복 | 현재 배포 API 문서에는 반복 해제를 표현하는 요청 스펙이 없다. `routine` 생략은 반복 유지로 처리되므로 조용히 저장하지 말고, 지원 계약이 확정될 때까지 반복 해제를 막고 안내한다. |

- `SINGLE`은 내용, 목표, 날짜, 시간, 카테고리 등 선택 회차의 값만 변경한다. 함께 보낸 반복 설정은 서버가 반영하지 않는다.
- 사용자가 반복 주기, 반복 기간 또는 반복 요일을 변경한 경우 `SINGLE`을 비활성화하거나 선택지에서 제외하고 `해당 날짜 이후 수정` 또는 `전체 반복 투두 수정`을 선택하도록 안내한다.
- 단순히 반복 설정 입력값을 생략해 반복을 해제하거나 변경하려고 하지 않는다. 서버에서는 기존 반복 연결이 유지된다.

### 3. API 요청 계약

수정은 기존 엔드포인트를 사용한다.

```text
PUT /todos/{id}
```

공통 요청 원칙은 다음과 같다.

- `date`와 1~30자의 `content`는 항상 보낸다.
- `goalId`, `time`, `category`는 수정 전 값을 유지하려는 경우에도 명시적으로 보낸다. 특히 `goalId` 생략 시 목표 연결이 끊기고 `time` 생략 시 시간이 삭제될 수 있다.
- `routine`을 보내면 `routineUpdateType`을 반드시 함께 보낸다.
- `routineUpdateType`이 `FROM_DATE` 또는 `ALL`이면 `duration`과 `repeatType`을 포함한 `routine`을 반드시 함께 보낸다.
- `routine.repeatDays`는 `string[] | null`로 수용하고 사용자가 변경하지 않은 경우 최신 상세 조회값을 그대로 보존한다.
- `repeatType`은 배포 API가 지원하는 `DAILY`, `WEEKLY`, `BIWEEKLY`, `MONTHLY`만 전송한다.
- 날짜는 `yyyy-MM-dd`, 시간은 `HH:mm`, 범위 enum은 정의된 상수만 전송 전에 검증한다. 형식 오류나 잘못된 범위 enum이 현재 서버에서 500으로 응답할 수 있다.
- 성공은 `200` 빈 바디로 처리하며 응답에서 수정 결과나 새 ID를 읽지 않는다.

`FROM_DATE`와 `ALL`에 보낼 `routine`은 수정 화면을 열기 직전에 `GET /todos/{id}`로 조회한 값을 복사하고 실제 변경값만 덮어쓴다.

- `FROM_DATE`에서는 `routine.duration.startDate`를 서버가 기준일로 대체하지만, 클라이언트는 임의 계산하지 않고 상세 조회값을 그대로 보낸다.
- `ALL`에서는 전송한 `routine.duration.startDate`가 실제 전체 반복 시작일로 사용되므로 오래된 목록 캐시나 앞 구간의 기간을 보내지 않는다.
- `routine.repeatDays`가 `null`이면 본문 `date`의 요일을 기준으로 반복되므로, `null`을 임의의 빈 배열이나 기존 날짜의 요일로 치환하지 않는다.

### 4. 위험 안내와 확인 정책

다음 변경은 범위 버튼을 누른 뒤 실제 요청 전에 별도 확인을 거친다.

- `FROM_DATE`: 선택한 원래 회차를 포함한 이후 일정이 모두 다시 생성되고 ID가 바뀐다는 점을 안내한다.
- `ALL`: 과거 회차까지 포함해 반복 전체가 다시 생성된다는 점을 안내한다.
- 날짜, 요일, 반복 주기 또는 `repeatDays` 변경으로 새 회차의 날짜가 달라지는 경우: **기존 날짜와 일치하지 않는 회차의 완료 기록은 초기화된다**고 명시한다.
- 반복 종료일이 원래 회차의 기준일보다 앞선 `FROM_DATE` 요청은 확인 단계로 보내지 않고 폼 검증에서 차단한다.

확인 문구는 서버 내부 용어인 루틴이나 회차 ID보다 사용자가 이해할 수 있는 `이 날짜를 포함한 이후 투두`, `지난 투두`, `완료 기록` 표현을 우선한다.

### 5. 성공 후 재조회와 캐시 정책

- `SINGLE`은 ID가 유지되지만 범위별 흐름을 일관되게 하기 위해 성공 후 해당 날짜 목록과 개수 정보를 재조회한다.
- `FROM_DATE`와 `ALL`은 낙관적 업데이트를 하지 않는다. 응답 바디와 새 ID가 없으므로 서버 조회 결과만 화면의 정답으로 사용한다.
- `FROM_DATE`와 `ALL` 성공 시 현재 보이는 날짜뿐 아니라 `todos` 루트 아래 캐시된 모든 일간·주간 목록과 날짜별 개수 쿼리를 무효화한다.
- 폼에서 날짜를 옮긴 경우 수정 전 날짜와 수정 후 날짜가 모두 갱신돼야 한다.
- 재조회가 끝나기 전에 기존 ID로 완료, 수정, 삭제 후속 요청을 보내지 않는다.
- 네트워크 응답이 유실됐다고 같은 변경 요청을 자동 재시도하지 않는다. 먼저 목록을 조회해 반영 여부를 확인하고, 이미 교체된 ID로 재요청해 404가 발생하지 않게 한다.

## 테스트 시나리오

1. 반복 투두에서 `SINGLE`, `FROM_DATE`, `ALL` 버튼을 각각 선택하고 요청 범위와 결과 확인
2. 중간 회차에서 `FROM_DATE` 선택 시 기준일 이전 회차가 유지되는지 확인
3. 폼 날짜를 다른 요일로 옮긴 뒤 `FROM_DATE`를 선택하고 원래 회차 날짜가 절단 기준인지 확인
4. 날짜·요일 변경 시 완료 기록 초기화 경고 노출 및 취소 동작
5. 반복 설정 변경 시 `SINGLE` 비활성화 또는 미노출 확인
6. 비반복 투두 일반 수정 시 `routine`과 범위가 모두 생략되는지 확인
7. 비반복 투두에 반복을 추가할 때 `ALL`, `routine`, 본문 날짜와 같은 `startDate`가 전송되는지 확인
8. 반복 투두에서 반복 해제를 시도할 때 지원되지 않는 저장이 차단되는지 확인
9. `goalId`, `time`, `category`, `repeatDays: null` 및 다중 `repeatDays`가 수정 후 보존되는지 확인
10. 수정 직전 상세 조회값의 `routine.duration`을 사용하고 오래된 목록 캐시를 사용하지 않는지 확인
11. `FROM_DATE`와 `ALL` 성공 응답이 빈 바디여도 오류 없이 처리되는지 확인
12. `FROM_DATE`와 `ALL` 성공 후 기존 ID가 사라지고 재조회한 새 ID로 후속 조작하는지 확인
13. 날짜를 옮긴 수정 후 이전·새 날짜 및 캐시된 다른 주간 목록과 개수가 모두 갱신되는지 확인
14. 요청 중 중복 클릭 방지, 실패 시 폼 유지, 오류 안내 및 수동 재시도 확인
15. 누락된 `routine`, 잘못된 날짜·enum, 종료일 역전, 콘텐츠 0자·31자에 대한 클라이언트 검증 확인
